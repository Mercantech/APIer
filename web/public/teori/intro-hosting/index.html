Intro og hosting

Hvad Blazor er, hvordan det minder om andre SPA-frameworks, og forskellen på Server, WebAssembly og Hybrid — plus hvordan jeres UI alligevel taler HTTP med OpgaverAPI.

Hvornår vælge Blazor? Når I allerede arbejder i C#/.NET og vil dele logik med API-projekter — typisk GUI + OpgaverAPI i samme klasseforløb.

Tjek dig selv før du går videre

  • Du kan skelne UI-sync (SignalR) fra REST-kald til OpgaverAPI.
  • Du kan nævne én fordel og én ulempe ved Blazor Server.
  • Du har afspillet hosting-animationen (Server vs WASM).

Blazor er Microsofts moderne web-UI-stack: du bygger genbrugelige Razor-komponenter med C#, HTML og CSS. Udvikleroplevelsen minder om React, Svelte og Vue — komponent-tænkning, state, routing — men runtime-sproget er .NET i stedet for JavaScript.

Et Razor-komponent blander markup og C# i samme fil (.razor). Det gør det nemt at opdele UI i små dele: et Pokémon-kort, en LoL-champion-række, en søgebar — og lade dem dele services der kalder OpgaverAPI.

SPA og API — to lag

Selv om Blazor «føles» som én app, er data næsten altid HTTP JSON mod et backend API. Browseren (eller server-circuit) kører UI; HttpClient henter Pokémon-listen — samme model som katalogets demos.

Tre hosting-modeller

Hvor kører koden?

Skift mellem Server og WASM — prikkerne viser trafikretning i realtid.

BrowserUI / events
ASP.NET.NET + Razor

Blazor Server

Komponenter kører på serveren. UI-events og opdateringer går over en SignalR-forbindelse (WebSocket eller long polling). Fordele: lille første download, fuld .NET på serveren, nem debug i Visual Studio. Ulemper: latency ved hver interaktion, server skal holde circuit alive.

Blazor WebAssembly (WASM)

.NET runtime og jeres DLL’er downloades til browseren. Efter initial load kører event handlers lokalt. API-kald til OpgaverAPI er stadig almindelig HTTP — WASM ændrer ikke REST-kontrakten. Ulemper: større payload, forretningslogik er synlig, begrænset tråd-model.

Blazor Hybrid

Razor i native shell (MAUI, WPF med WebView). Relevant hvis I senere laver mobil/desktop — samme komponent-syntaks, anden distribution.

Render modes (.NET 8+)

Blazor Web App kan mixe static server render og interaktiv Server/WASM per komponent eller globalt. Undervisningsprojekter: vælg Interactive Server globalt indtil I har grund til WASM.

@rendermode InteractiveServer

@* Eller i Program.cs: AddInteractiveServerRenderMode() *@

Hvornår Interactive WASM per komponent? Når én tung widget skal køre client-side uden at flytte hele appen — sjældent i første projekt. Start med global Server; skift kun med begrundelse i dokumentation.

Relation til jQuery og «klassisk» web

I jQuery manipulerede I DOM direkte og kaldte $.ajax. I Blazor beskriver I hvordan UI skal se ud givet state; frameworket diff’er DOM. AJAX erstattes af HttpClient + async metoder — bedre struktur til større apps som et Pokémon-dex projekt.

Hvornår jQuery stadig nævnes? Kun som kontrast — undervisningsmål er komponent + DI + typed HTTP, ikke $('#list').html(...).

Faldgrube: At antage at «Blazor Server = ingen HTTP» — hver side der henter OpgaverAPI laver stadig HTTP fra server-processen. SignalR er kun UI-sync, ikke jeres REST-kald.
